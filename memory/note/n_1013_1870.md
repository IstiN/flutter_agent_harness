# Note: n_1013_1870

CI triage: when a v* tag run's core-test shard dies at the job wall-clock timeout and the job logs have expired (gh api .../logs → BlobNotFound), the `step-timings` artifact (retention 14d) still gives per-step durations — healthy setup steps + a `dart test` step that never finished = load-sensitive ubuntu-24.04-arm runner flake, not a product bug; reproduce locally with the exact shard list (`python3 scripts/shard_files.py scripts/test_shards.json N` stdout only, warnings are stderr) before concluding. Recovery: `gh run rerun <run-id> --failed` — shard reruns green (~8 min), the Quality gate evaluates green seconds later (that is the ticket's "ref goes green" condition), and the release tail (binaries → provenance → publish → vpinned) re-runs automatically as gate dependents. The watchdog's degraded-runner retrigger is pull_request-only, so tag runs have no automatic recovery — rerun is the only remedy for an immutable tag ref. Seen: gh-1875 / v1.0.642 run 40178875259, shard 2/4, 2026-10-25.
