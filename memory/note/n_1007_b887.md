# Note: n_1007_b887

gh-1759 fix (2026-10-21): the wasmrun-xcframework-v0.1.0 actions/cache entry is NOT durable — the repo's daily cache churn (fresh macos-pods-<sha> keys each run) LRU-evicts it within ~37h (saved 10-20 06:02Z, gone 10-21 19:03Z), so the build-macos.yml WasmRun restore step's download fallback must be self-sufficient on cold days. The self-hosted runner's link to the GitHub release CDN swings 40–320KB/s run-to-run; the asset is 97,238,501 bytes (sha256 aca903d7…548a98). Fix shape (pinned by test/wasmrun_restore_budget_test.dart): the per-arch /tmp/WasmRun.xcframework-<arch>.zip partial PERSISTS across daily runs (no pre-loop rm -f — that was gh-1759's treadmill), pre-loop sha256 gate skips the download when the persisted zip is complete (avoids the HTTP-416 trap), incomplete downloads KEEP the partial (byte-size vs pinned ASSET_BYTES decides keep-vs-purge), only wrong-content is purged; budget 4 × 240s attempts under timeout-minutes: 20. Verification technique that worked without CI: extract the run: block with sed, substitute ZIP/DEST/URL/digest/max-time, serve a Range-capable throttled python http server (BaseHTTPRequestHandler 206 + per-chunk sleep), and drive old-vs-new scenarios — old script's partial never grew past 3 attempts across runs, new one banked 4 attempts' worth then resumed to completion cross-run. Watch out: only ONE driver at a time (concurrent -C - writers to the same zip silently share progress and fake the results), and this runner's bash tool executes commands via dash — no process substitution/functions with <() in inline commands; write a script file and bash it.
