# Note: n_0481_02c2

Worktree placement policy (added 2026-09-02, fa session with user). The user runs multiple fa LLM loops in parallel; the shared flutter_agent checkout is THEIR primary workspace, never just one agent's. After two prior sessions left orphan worktrees at /Users/Uladzimir_Klyshevich/git/{fa-cube-feat,fa-dap-pr3}/ the user asked for a convention. Final decision: when a worktree is genuinely required, place it INSIDE flutter_agent/.worktrees/<name>/ (NOT in the parent directory). User reasoning: (a) dot-prefix keeps it visually separate in ls; (b) it lives with the repo it branches from, so the worktree's git linkage is unambiguous; (c) it can be removed wholesale with `rm -rf .worktrees/`. Policy items: (1) by default DO NOT create a worktree — for review, gh api + git fetch + git show / git diff origin/<branch>..HEAD is enough; (2) if a worktree is genuinely required (local dart test/analyze on a non-current branch), ASK the user first whether to proceed and confirm .worktrees/<name>/ placement; (3) use `git worktree add --detach .worktrees/<name> origin/<branch>` against the remote tracking ref, NEVER the local branch ref which the user may have moved on; (4) `git worktree remove` the moment done, do not leave orphans; (5) append `.worktrees/` to .gitignore ONLY after confirming — silent .gitignore edits conflict with parallel agents who may already have it dirty (incident: I added .worktrees/ to .gitignore while parallel agent had unrelated dirty changes — caused concern, reverted immediately); (6) never git stash pop/drop/apply the user's WIP; (7) never run heavy commands (full dart test, full dart analyze) in the shared checkout — competes with the user's own LLM loop for CPU/IO; (8) communicate with peer agents through the inbox fabric, never by editing their files. This policy is also documented at AGENTS.md under `## Working in parallel: shared checkout + worktrees`. Supersedes the implicit assumption that agents can freely create worktrees at ../<name>/ in the parent directory.
