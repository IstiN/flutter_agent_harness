## Root Cause Analysis

**Bug**: After a successful CodeMie re-authorization, the "Session expired — Authorize" card stays in the chat transcript, still offering an Authorize button for a session that was just fixed.

**Root cause**: A failed provider run persists its `[[auth-expired:codemie]]`-marked error into the transcript as an actionable auth-expired card (`AgentService._finalizeAssistant` in `flutter_app/lib/services/agent_service_assistant.dart` adds the `role: 'tool', toolName: 'error'` message; `packages/fa_ui/lib/src/chat/chat_message_tile.dart` renders it via `_authExpiredCard`). The recovery flow (`runCodemieSsoFlow` → `saveCodemieConnection` in `flutter_app/lib/services/codemie_sso_flow_steps.dart`) reconfigures the service — which clears the top error banner (`AgentService.reconfigure` sets `error = null`) — but nothing touches the transcript, so the stale card keeps claiming the session is expired. The user is invited to re-authorize an already-refreshed session (issue #623 screenshot).

**Impact**: Every successful CodeMie sign-in launched from the auth-expired card (chat screen, session chat sheet) or from Settings leaves the red expired-session card in the live transcript. Users reasonably conclude the authorization failed and tap Authorize again or resend into confusion. The card is a live-transcript artifact only (session reload projects the record without the card), so the confusion covers the whole live session after the fix of #586.

**Fix approach**: On a successful connect, resolve every auth-expired card in the live transcript. `AgentService` gets `resolveAuthExpiredCards()` (transcript part file): remove all messages carrying an `[[auth-expired:<id>]]` marker and drop a single system note ("Authorization successful — … try sending your message again.") at the position of the newest card, then notify listeners. `saveCodemieConnection` calls it right after `service.reconfigure(config)`, so every success path (card Authorize tap, extension cookie sign-in, Settings re-login, onboarding) clears the stale card in one place.

**Previous attempt**: PR #593 (issue #586) anchored the re-auth flow on the root navigator so the SSO prompts survive transcript rebuilds — the flow now completes, but the success path never reconciles the transcript, which is what this issue reports.
